# 工程方法

这份文档只保留适用于后续开发的规则。阶段历史交给 Git，当前状态写在 `docs/status/`，具体取舍写在
`docs/decisions/`。

## 先判断是功能缺口还是地基问题

出现下面任一信号时，先检查抽象边界：

- 同步与异步生命周期反复互相包裹；
- 同一提交、回滚或投递逻辑在三个地方重复；
- 加一个 source、tool 或 memory engine 要改多个无关模块；
- 测试构造一个组件却必须把整个 runtime 都造出来。

配置是可序列化的值，服务是有生命周期的对象。两者分开，才能明确谁创建、谁持有、谁关闭。

## 验证生产调用链

模块有单测不代表它接进了系统。每个新能力都要回答：

1. 生产入口在哪里？
2. 上游真实提供什么数据？
3. 下游谁消费结果？
4. 成功、失败和进程崩溃分别提交什么？
5. 资源在何时关闭？

消费方测试尽量使用真实上游生成的数据，不要手工造一个“理想 metadata”证明自己的假设。

## 分清测试与实弹

自动化测试适合验证合同、边界、错误语义和回归。真实 provider、真实 Channel 与跨组件数据形状还需要
在线 smoke。报告时使用明确口径：已测试、已在线验证、未验证。统一证据写在
[验证记录](../operations/verification.md)。

## 迁移职责时列清单

把驱动权从 A 移交给 B 前，列出 A 的全部职责，包括等待、锁、游标推进、审计写入和失败保护。逐条确认
B 接住后再删除旧路径。相关实例见[决策 0003](../decisions/0003-consolidation-handover.md)。

## 不长期保留过渡态

迁移完成后删除旧目录、兼容入口、双写和无调用代码。保留两套路径不是稳妥，而是让真实 owner 变得无法
判断。确需兼容时，要写清删除条件和截止边界。

## Reference 使用边界

Reference 可以提供开发期结构和合同依据，但最终实现必须成为 Kirakira 仓库内的本地源码。运行、构建、
测试、doctor 和文档都不能依赖 Reference checkout。

复用纯算法、协议和数据结构时优先直接采用经过审计的实现；涉及本项目 owner、生命周期和持久层时，按
同一合同接到 Cloud adapter 中。任何有意差异都写进[Cloud 总方案](../cloud-engineering/plan.md)。

## 文档维护

- 文档唯一入口是 [docs/INDEX.md](../INDEX.md)；
- 当前事项只写在 [status/current.md](../status/current.md)；
- 同一事实只保留一个权威位置；
- 代码改名、工具改语义或 owner 迁移时，同一提交更新文档；
- 不保存会快速过期、又没有自动验证来源的名单和数字；
- 删除文档前把仍有效的合同合并到对应分类，不留“仅供参考”的垃圾堆。
